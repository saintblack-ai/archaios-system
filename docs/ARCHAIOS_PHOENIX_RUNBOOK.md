# Archaios Phoenix Recovery Runbook

Status: safe-prep only
Last updated: 2026-06-18

Compliance note: Do not transact or collect regulated data until licensed.

## Mission Frame

Archaios Phoenix is the controlled replacement path for the unreachable Supabase project. Until licensing is finalized, this runbook is limited to documentation, architecture hardening, migration planning, security review, SOPs, and dry-run test scripts. Do not create a production revenue flow, process real checkout payments, or collect regulated data from users.

## Decision Gate

Current recommendation: No-Go for production replacement execution.

Go for safe prep:

- Document environment ownership.
- Validate migration order.
- Prepare dry-run smoke tests.
- Prepare secret rotation SOPs.
- Prepare operator checklists.

No-Go until all are true:

- Licensing/compliance approval is recorded.
- Supabase replacement project is authorized.
- A vault location is approved for secrets.
- `SUPABASE_ACCESS_TOKEN` or dashboard access is available.
- `CLOUDFLARE_API_TOKEN` is available for Worker secret audit/update.
- GitHub repository variables/secrets can be set by an authorized operator.
- Stripe remains in test mode until licensing is cleared.

Abort immediately if any of these occur:

- A real payment flow is started before licensing approval.
- A real customer lead or regulated data record is submitted during pre-license testing.
- A service-role key appears in chat, terminal output, Git history, frontend env, or docs.
- A migration fails after partially modifying auth, profiles, or subscriptions.
- A new Supabase project is created before approval is recorded.

## Security And Secrets Policy

### Handling Rules

1. Never paste keys in chat, issues, PR comments, docs, screenshots, or logs.
2. Store secrets only in the approved vault and platform secret stores.
3. Use local `.env` files only for local development, and keep them ignored by Git.
4. Do not copy service-role keys into `VITE_*`, `NEXT_PUBLIC_*`, or any browser-exposed variable.
5. Validate JWT role before storing Supabase keys:
   - anon key must decode to `role: anon`.
   - service-role key must decode to `role: service_role`.
6. Rotate any key that was pasted into chat, committed, exposed in logs, or shared outside the vault.
7. Use Stripe test mode until licensing and launch approval are complete.

### Rotation Plan

| Secret | Rotation Trigger | Rotation Steps |
| --- | --- | --- |
| Supabase anon key | Project replacement, suspected exposure, scheduled quarterly review | Generate/reveal new anon key, update GitHub/Vercel browser env, rebuild frontend, verify sign-in. |
| Supabase service-role key | Any exposure, project replacement, staff/access change | Generate/reveal new service-role key, update Cloudflare/Vercel server secret, redeploy Worker, verify `/api/leads` and webhook write in safe mode. |
| Cloudflare Worker secrets | Any platform/operator change or key exposure | Use `wrangler secret put`, redeploy, run dry-run smoke suite. |
| `CLOUDFLARE_API_TOKEN` | Operator offboarding, exposure, permission change | Revoke old token in Cloudflare, issue least-privilege token, store in vault. |
| Stripe secret key | Exposure or mode transition | Rotate in Stripe dashboard, update Worker secret, verify checkout in test mode only. |
| Stripe webhook secret | Webhook endpoint recreation or exposure | Regenerate endpoint secret, update Worker secret, verify unsigned payload is rejected. |
| Stripe price ids | Product/pricing change | Update Worker price secrets and public docs, verify `/api/pricing` matches offer. |
| GitHub secrets | Exposure, repo ownership change, environment split | Replace via GitHub Actions secrets UI/CLI, rerun build. |

## Rollback And Stop Criteria

Pre-license rollback is mostly procedural because no production mutation should happen.

Stop and document:

- Any command tries to create a production project.
- Any command tries to process a payment.
- Any command writes a real lead.
- Any secret value appears in stdout/stderr.
- Any migration plan requires destructive changes.

Licensed rollback plan:

- Keep previous Worker deployment available until replacement smoke checks pass.
- Do not promote frontend env changes until Worker health and pricing pass.
- If migration fails, stop before secrets are updated.
- If Worker deploy fails, keep old frontend pointing to old Worker URL.
- If checkout dry-run fails, do not enable paid dashboard claims.

## Worker And Frontend Test Plan

Safe checks:

- `GET /api/health` should return HTTP 200.
- `GET /api/pricing` should return HTTP 200 and free/pro/elite tiers.
- Unsigned `POST /api/stripe/webhook` should return HTTP 400 and reject missing Stripe signature.
- Unsigned `POST /api/stripe/checkout` should reject with unauthorized response.
- Paid dashboard unlock logic can be tested with local unit/dry-run subscription objects.

Conditional checks:

- `POST /api/leads` should be stubbed or skipped until licensing allows collection.
- If a lead write is approved, use a test-only address and record it as a controlled verification.
- Do not run real Stripe checkout until licensing is finalized.
